  2. 2

OrderOps Agent

A support agent for an online store that answers policy questions, looks up the customer's own orders and proposes refunds a person approves. It runs publicly, with every decision, its cost and its latency visible.

  • An agent graph with four routes: policy answers from the store's documents, order lookups through tool calls, refund requests, and a refusal for anything out of scope. It remembers each conversation and useful facts about each customer, in PostgreSQL.
  • Refund rules are enforced in code, not in the prompt, and the agent pauses until an operator approves or rejects.
  • Anthropic, OpenAI and AWS Bedrock behind one interface, with automatic failover and prompt caching.
  • Runs on one AWS EC2 instance behind Caddy with automatic TLS, using an IAM instance role, with no access keys on the server. GitHub Actions checks every pull request, and each merge deploys through OIDC, ECR images tagged by commit, SSM, a smoke test and automatic rollback.
  • Every request is traced in PostgreSQL (route, tools, provider, failover, tokens, cost, latency) and sent to Langfuse as spans per graph node. A dashboard in the demo shows p50/p95 latency, cost per conversation (about $0.012 on a demo-sized load) and failover rate.
  • 41 eval cases, 13 of them adversarial: 41/41 on the latest run, and a regression gate in CI on every pull request. 457 automated tests.

Decisions and what broke

Why rules live in code

The model turns the message into a structured request; four plain functions decide if it's allowed. A prompt can be talked out of a rule. A function can't.

Why the agent only sees your orders

The customer's login token travels with every tool call, so authorization stays where it already lived.

Why one EC2 instance

It's a demo. ECS Fargate with RDS and a load balancer costs several times more; it's the documented next step to scale.

What broke

Saving each trace blocked the streamed reply. The write now happens at the end of the request and is best-effort, so a failure is logged and never reaches the user.

EDGAR Analyst

Answers questions about public companies from their SEC filings and earnings calls, citing the exact filing and section. Built in one week.

  • Section-aware chunking over 10-K and 10-Q filings and earnings-call transcripts, about 2,400 cited chunks.
  • Refuses before calling the model when the evidence is weak, so off-topic questions cost nothing.
  • 22 hand-labeled eval pairs scored for citation accuracy and answer relevance.
  • About 2 seconds and $0.002 per answer, logged per query. 122 automated tests.
  • Python
  • Anthropic API
  • ChromaDB
  • sentence-transformers
  • Pydantic
  • pytest
What the eval showed

Citation accuracy is 27%. The model isn't inventing things: the passage the eval expects often isn't among the five retrieved, so it's a retrieval problem, not a generation one. Next I'll test a larger top-k, a stronger embedding model and section titles inside the embedded text.
